## الهدف

تشرح هذه الصفحة كيفية نشر **ProPM Agent** من **Azure Marketplace**، ثم كيفية إنهاء تشغيل بيئتك بشكل صحيح.

النقطة الأساسية التي يجب تذكرها بسيطة:

- **Azure Marketplace يثبت المنصة**؛
- يتيح حقل **LLM Provider** اختيار **عائلة مزود الذكاء الاصطناعي** المستخدمة في البيئة؛
- تكتمل **عملية التشغيل النهائية** لمزود الذكاء الاصطناعي لاحقا في **إدارة المنصة > إعدادات مزود الذكاء الاصطناعي**.

بعبارة أخرى، لا يكفي النشر وحده لجعل مزود الذكاء الاصطناعي قابلا للاستخدام مباشرة من قبل المستخدمين النهائيين.

## ما يقرره المسؤول أثناء النشر

أثناء معالج Marketplace، يقرر المسؤول أساسا:

- أي **اشتراك Azure** ستنشر فيه الحل؛
- أي **مجموعة موارد** وأي **منطقة**؛
- أي **مجموعات Entra** ستدير المنصة؛
- أي **مزود ذكاء اصطناعي رئيسي** ستستخدمه البيئة؛
- أي قواعد أولية لـ **CORS** و**السجلات** و**المراقبة** و**الشبكة** ستطبق.

## ما يكتمل بعد النشر

بعد التثبيت، يجب على مسؤول المنصة أيضا:

1. فتح **إدارة المنصة**؛
2. الانتقال إلى **إعدادات مزود الذكاء الاصطناعي**؛
3. إكمال الحقول الخاصة بالمزود المختار؛
4. حفظ الإعداد؛
5. تشغيل **Validate**؛
6. تشغيل **Test**؛
7. تشغيل **Activate**؛
8. ثم تأكيد المزود المستخدم فعليا في **سجل الذكاء الاصطناعي**.

## قبل بدء النشر

حضّر على الأقل:

- **اشتراك Azure** الهدف؛
- **مجموعة الموارد** الرئيسية و**المنطقة**؛
- **معرفات كائنات Entra** لمسؤولي المنصة؛
- **مستخدمي bootstrap** المحتملين؛
- اختيار **مزود الذكاء الاصطناعي** الذي سيستخدم في البداية؛
- إذا اخترت **Azure OpenAI**، فالمسؤول الذي سينهي لاحقا **LLM deployment name** في الإدارة؛
- **أصول CORS** الإضافية إذا كان يجب استدعاء التطبيق من نطاقات أخرى؛
- خطة عنونة متوافقة مع **VNet CIDR**؛
- التحضير لأول اختبار اتصال و**redirect URIs Entra**.

## الخطوة 3 — اختيار مزود الذكاء الاصطناعي أثناء النشر

لا يخدم حقل **LLM Provider** Azure OpenAI فقط. فهو يتيح اختيار أحد مزودي الذكاء الاصطناعي الظاهرين في المنتج.

### الحالات الأربع التي يجب معرفتها

| مزود الذكاء الاصطناعي | متى تختاره | الميزة الرئيسية | ما تقرره أثناء النشر | ما تكمله لاحقا في الإدارة |
| --- | --- | --- | --- | --- |
| **Azure OpenAI** | إذا كانت بيئتك متمحورة بالفعل حول Azure، وEntra، والشبكة الخاصة، وحوكمة Microsoft | تكامل طبيعي مع منظومة Azure | تختار Azure OpenAI كمزود هدف | تملأ endpoint، وإصدار API، ووضع المصادقة، وخاصة **LLM deployment name** |
| **OpenAI** | إذا كانت مؤسستك تريد استخدام منصة OpenAI مباشرة | مسار بسيط ومباشر | تختار OpenAI كمزود هدف | تكمل عنوان URL المستخدم، والمفتاح أو مرجع السر، والنموذج الافتراضي، ثم تتحقق وتفعل |
| **OpenRouter** | إذا كانت مؤسستك تريد مقارنة عدة عائلات نماذج عبر نقطة دخول واحدة | رابط واحد لعدة نماذج وسيناريوهات توجيه | تختار OpenRouter كمزود هدف | تكمل Base URL، والمفتاح، والنموذج الافتراضي، ثم تتحقق وتفعل |
| **OpenAI-compatible** | إذا كانت مؤسستك تستخدم gateway شريكا، أو endpoint مؤسسيا، أو runtime متوافقا | يتيح ربط تنفيذ متوافق من دون تغيير المنتج | تختار OpenAI-compatible كمزود هدف | تكمل endpoint الدقيق، والمصادقة، والنموذج أو النشر المتوقع |

### قاعدة بسيطة يجب تذكرها

النشر **يعين المزود**. الإدارة **تجعل المزود عاملا**.

## ما يدركه المستخدم النهائي فعليا

بالنسبة إلى المستخدم النهائي، يؤثر المزود المختار في:

- **النماذج** المستخدمة فعليا؛
- مستوى **الحوكمة التقنية** الذي تفرضه المؤسسة؛
- الطريقة التي يدير بها فريق الإدارة **المفاتيح** و**الأسرار** و**عمليات النشر**؛
- أحيانا **سرعة التشغيل** أو **مرونة تغيير النموذج**.

ومع ذلك، لا يحتاج المستخدم النهائي إلى فهم كل آلية التثبيت. حاجته هي أن يكون المزود:

- معدا؛
- متحققا منه؛
- مختبرا؛
- مفعلا؛
- قابلا للتتبع في **سجل الذكاء الاصطناعي**.

## الحالة 1 — **Azure OpenAI**

توضح اللقطة أدناه السلوك عندما يتم ضبط **LLM Provider** على **Azure OpenAI**.

![اختيار Azure OpenAI مع إشارة إلى الإعداد اللاحق في الإدارة](/img/deploiement/fr/deploiement-03-azure-openai-marketplace-managed-annotated.svg)

### متى يكون هذا الاختيار مناسبا

اختر **Azure OpenAI** عندما تكون مؤسستك:

- تعمل بالفعل في الغالب على Azure؛
- تريد إطارا قويا حول **Entra**، والشبكة، وحوكمة Microsoft؛
- تريد اختيار عمليات نشر دقيقة في مورد Azure OpenAI لديها.

### ما يعنيه ذلك أثناء النشر

أثناء Marketplace:

- تختار **Azure OpenAI** كمزود؛
- يمكن أن يحضر التثبيت اتصال Azure المرتبط؛
- بالنسبة إلى مسار Azure OpenAI المدار، يستطلع النشر الآن عدة مناطق Azure OpenAI ويختار تلقائيا أفضل منطقة متاحة بحسب التوفر الحقيقي للنماذج؛
- يحتفظ runtime بأسماء مستعارة ثابتة لنشر Azure OpenAI تسمى `chat` و`embeddings`؛
- لم يعد اختيار نموذج runtime الدقيق مثبتا عالميا وقت النشر.

### ما يزال يجب فعله بعد التثبيت

بعد النشر، افتح **إدارة المنصة > إعدادات مزود الذكاء الاصطناعي** وأكمل أو أكد:

- **منطقة** Azure OpenAI التي اختارها النشر؛
- **كتالوج النماذج** المكتشف فعليا لتلك المنطقة؛
- **النموذج الموصى به** الذي تقترحه المنصة؛
- النموذج المحدد حاليا والمتزامن خلف الاسم المستعار الثابت `chat`؛
- حالة الاتصال والتحقق.

### خصوصية مهمة

إذا كان النشر قد ثبت بالفعل سرا أو مفتاحا لـ Azure OpenAI، فقد تشير الواجهة إلى أن **API key مرئيا للمستخدم** غير مطلوب في هذا النموذج. في هذه الحالة، يركز المسؤول أساسا على اختيار النموذج، واختبارات الاتصال، ومزامنة النشر.

إذا اختار مسؤول عن قصد جيلا من GPT أدنى من **GPT-5**، فيجب أن تعرض الواجهة تحذيرا واضحا قبل الحفظ. يجب أن يؤدي حفظ نموذج Azure OpenAI جديد بعد ذلك إلى مزامنة نشر Azure OpenAI الحقيقي خلف الاسم المستعار `chat`، من دون مطالبة المستخدم بإعادة تسمية عمليات النشر يدويا.

## الحالة 2 — **OpenAI**

### متى يكون هذا الاختيار مناسبا

اختر **OpenAI** عندما تريد مؤسستك استخدام واجهات API الخاصة بـ OpenAI مباشرة، من دون المرور عبر Azure OpenAI أو gateway وسيطة.

### مزايا عملية

- إعداد أكثر مباشرة عادة؛
- قراءة بسيطة لفريق يوحد استخداماته بالفعل على OpenAI؛
- من دون إدارة **اسم نشر Azure**.

### ما تقرره أثناء النشر

أثناء Marketplace، تقرر ببساطة أن البيئة ستستخدم **OpenAI** كمزود رئيسي.

### ما يزال يجب فعله بعد التثبيت

في **إعدادات مزود الذكاء الاصطناعي**، أكمل بعد ذلك:

- **Base URL** أو endpoint المستخدم من المنتج؛
- **النموذج الافتراضي**؛
- **مفتاح API** أو **مرجع السر**؛
- تسلسل **Save → Validate → Test → Activate**.

### الأثر على بيئة المستخدم

لا يحتاج المستخدم النهائي إلى رؤية هذه الإعدادات. المهم هو أن يكون المسؤول قد أكد الاتصال والنموذج المستخدم فعليا.

## الحالة 3 — **OpenRouter**

### متى يكون هذا الاختيار مناسبا

اختر **OpenRouter** عندما تريد مؤسستك الوصول إلى عدة عائلات نماذج عبر **نقطة دخول واحدة**، مثلا لمقارنة النتائج أو ضبط التوجيه بسهولة أكبر.

### مزايا عملية

- رابط واحد على مستوى المنصة؛
- مفيد لمقارنة عدة نماذج؛
- عملي عندما تريد المؤسسة الحفاظ على قدر من مرونة التوجيه.

### ما تقرره أثناء النشر

أثناء Marketplace، تشير إلى أن البيئة ستستخدم **OpenRouter** كمزود رئيسي.

### ما يزال يجب فعله بعد التثبيت

في **إعدادات مزود الذكاء الاصطناعي**، أكمل بعد ذلك:

- **Base URL**؛
- **مفتاح API** أو مرجع السر؛
- **النموذج الافتراضي**؛
- ثم شغل **Save → Validate → Test → Activate**.

### مثال بسيط

تريد مؤسستك الانطلاق بسرعة، ومقارنة عدة نماذج، ثم تثبيت اختيارها. يكون **OpenRouter** عندها مرشحا جيدا لمرحلة تحديد أولى.

## الحالة 4 — **OpenAI-compatible**

### متى يكون هذا الاختيار مناسبا

اختر **OpenAI-compatible** عندما لا تستخدم مؤسستك OpenAI مباشرة ولا Azure OpenAI، بل **endpoint متوافقا**، على سبيل المثال:

- gateway مؤسسية؛
- حل شريك؛
- runtime متوافق مستضاف ذاتيا.

### مزايا عملية

- يتيح ربط مزود متوافق من دون تعديل ProPM Agent؛
- مفيد عندما تتطلب بنية مؤسستك نقطة دخول ذكاء اصطناعي محددة؛
- خيار جيد لمستأجر يريد الحفاظ على طبقة تحكم أو توجيه داخلية.

### ما تقرره أثناء النشر

أثناء Marketplace، تشير إلى أن البيئة ستستخدم مزودا **OpenAI-compatible**.

### ما يزال يجب فعله بعد التثبيت

في **إعدادات مزود الذكاء الاصطناعي**، أكمل بعد ذلك:

- **Base URL الدقيقة** أو endpoint الدقيق؛
- **وضع المصادقة** المتوقع؛
- **المفتاح** أو **مرجع السر**؛
- **النموذج** أو **النشر** المتوقع؛
- ثم شغل **Save → Validate → Test → Activate**.

### نقطة يقظة

الموضوع الرئيسي هنا هو **التوافق الحقيقي** للـ endpoint. لا يكفي إعداد مسجل: زوج **Validate + Test** ضروري.

## المسار المشترك بعد التثبيت لكل مزودي الذكاء الاصطناعي

أيا كان المزود المختار في النشر، اتبع دائما هذا المسار:

1. افتح **إدارة المنصة**؛
2. انتقل إلى **إعدادات مزود الذكاء الاصطناعي**؛
3. حدد المزود الذي تريد تحضيره؛
4. أكمل الحقول المطلوبة؛
5. انقر **Save** للحفظ؛
6. انقر **Validate** للتحقق من الإعداد؛
7. انقر **Test** للتحقق من الاتصال الحقيقي؛
8. انقر **Activate** لجعل هذا المزود فعليا للمستخدمين النهائيين؛
9. ثم افتح **سجل الذكاء الاصطناعي** لتأكيد المزود المستخدم فعليا في تنفيذ حقيقي.

### كيفية قراءة أزرار الإدارة

| الزر | ما يعنيه |
| --- | --- |
| Save | يحفظ الإعداد المدخل |
| Validate | يتحقق من اتساق الحقول المطلوبة |
| Test | يتحقق من الاتصال الحقيقي بالمزود |
| Activate | يجعل المزود فعليا للمستخدمين النهائيين |

## التحقق قبل **التحقق + الإنشاء**

قبل بدء الإنشاء:

1. تحقق من الاشتراك، والمنطقة، ومجموعات الموارد؛
2. راجع مجموعات Entra ومستخدمي bootstrap المحتملين؛
3. أكد مزود الذكاء الاصطناعي المختار؛
4. إذا كان **Azure OpenAI** محددا، فحدد بوضوح من سينهي **LLM deployment name** بعد التثبيت؛
5. تحقق من معلمات الشبكة، والمراقبة، وكلمة المرور.

## بعد النشر

### الحد الأدنى من التحققات التقنية

1. سجل **عنوان URL للويب** المنشور فعليا؛
2. تحقق من عنوان URL الخاص بـ **API**؛
3. تحقق من توفر **`/runtime-config.json`**؛
4. تحقق من الاتساق بين عنوان URL المنشور و**redirect URIs Entra**؛
5. افتح **إدارة المنصة > إعدادات مزود الذكاء الاصطناعي** وأكد أن المزود المختار معد بالفعل؛
6. تحقق من أن الحالة المتوقعة تمر عبر **Configuration**، و**Validation**، و**Test**، ثم **Operational**.

### تحديثات بعد التثبيت من دون الرجوع إلى Marketplace

بعد تثبيت البيئة، تدار التحديثات المعتادة للتطبيق من **إدارة المنصة > النشر والتحديثات**. تحدث هذه العملية صور Container Apps القائمة وتنشئ مراجعات جديدة على موارد منشورة بالفعل.

لا يعيد هذا التدفق تشغيل عرض Azure Marketplace، ولا ينشئ مجموعة موارد جديدة، ولا يعيد إنشاء موارد النشر. ويستخدم لتطبيق صور ACR المعتمدة، والتحقق من الخدمات المرشحة، وتحديث الوسوم القابلة للتغيير عندما تسمح البيئة بذلك، والعودة إلى صورة سابقة عبر rollback عندما تكون المراجع متاحة.

قبل استخدامه، أكد أن هوية runtime تستطيع قراءة Container Apps وتعديلها عبر Azure Resource Manager، وأن `AZURE_SUBSCRIPTION_ID` وإحدى المتغيرات `AZURE_RESOURCE_GROUP_ID` أو `AZURE_RESOURCE_GROUP` أو `AZURE_RESOURCE_GROUP_NAME` معدة، وأن الصور الهدف تأتي من manifest تحديث، أو إعداد صور هدف، أو وسم تطبيق مصرح به.

أبق المرحلتين منفصلتين: Marketplace يثبت البيئة الأولية؛ **النشر والتحديثات** يحافظ على التثبيت القائم. لا يغطي زر الإدارة هذا ترحيلات مخطط قاعدة البيانات ولا تغييرات البنية.

### مصادقة Entra

بحسب نمط نشرك، تحقق من تسجيل تطبيق Entra أو أنجزه:

- `clientId`؛
- `authority` أو المستأجر؛
- `scopes`؛
- `redirectUri` و`postLogoutRedirectUri`؛
- عند الحاجة، واجهة API المعروضة وscopes الخاصة بها.

### أول اختبار وظيفي

بعد النشر، نفذ على الأقل:

- اتصالا بحساب مستخدم قياسي؛
- اتصالا بحساب إدارة متوقع؛
- فتح **المشاريع**؛
- فتح **لوحة التحكم**؛
- فتح **إدارة المنصة > إعدادات مزود الذكاء الاصطناعي**؛
- تنفيذ **Save → Validate → Test → Activate** على المزود المختار إذا لم يتم ذلك بعد؛
- التحقق من **سجل الذكاء الاصطناعي** لتأكيد المزود الفعلي وعائلة النموذج المستخدمة.

### معلومات لفريق الإدارة

بمجرد التحقق التقني من المنصة، انقل على الأقل:

1. **عنوان URL المنشور** القابل للاستخدام فعليا؛
2. **المستأجر** المتوقع وقاعدة دعوة حسابات **guest** عند الحاجة؛
3. أول مجموعة أو حساب اختبار؛
4. مزود الذكاء الاصطناعي الجاهز فعليا للاستخدام؛
5. صفحة [البدء السريع](./demarrage.md) التي يجب اتباعها لأول اتصال.

## نقاط تحكم مفيدة بعد التثبيت

| نقطة يجب التحقق منها | لماذا هي مهمة |
| --- | --- |
| عنوان URL المنشور وRedirect URIs Entra | تتجنب أول وصول محظور رغم نجاح النشر |
| مجموعات الإدارة ومستخدمو bootstrap | تضمن الدخول الأولي إلى الإدارة |
| مزود الذكاء الاصطناعي المختار | تتجنب الخلط بين مزود معلن فقط وآخر عامل فعليا |
| Validation وTest | تؤكد أن الإعداد لم يحفظ فقط، بل يمكن استخدامه |
| سجل الذكاء الاصطناعي | يؤكد المزود المستخدم فعليا في تنفيذ |
| مراقبة Azure | تضمن أن قابلية الرصد المطلوبة مفعلة |
